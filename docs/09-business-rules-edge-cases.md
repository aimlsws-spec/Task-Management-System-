# Document 9 — Business Rules & Edge Cases

Format: **Situation → recommended behaviour** (✱ = needs confirmation, see Q-list). All behaviours must be covered by an automated test.

| # | Situation | Recommended behaviour |
|---|---|---|
| 1 | **Employee leaves with pending tasks** | Deactivation is blocked from completing until the system lists open tasks; the user is disabled immediately (tokens revoked, `token_version++`), timer force-stopped (`auto_closed`). Open tasks keep their history, get `orphaned` flag, appear in the manager's (then dept head's, then CEO's) "Needs reassignment" queue, reminders pause for them, a single notification goes to the resolved reviewer. Reassign uses `task_assignments` (history kept; deadline unchanged unless changed explicitly). ✱Q12 |
| 2 | **Manager changes** | Close the old `reporting_relationships` row, open a new one with `effective_from`. Future notifications/scope use the new manager; past history/audit/reports "as-of" use the old one. Pending reviews assigned to the old manager move to the new one (notified). Old manager loses access immediately. |
| 3 | **Department head changes** | Update `departments.head_employee_id` (history in `activity_logs`), swap role grant. Tasks the old head *created* stay attributed to them; review authority and notifications follow the *current* head. Old head keeps read access only if still in scope by another rule. |
| 4 | **Employee receives many tasks** | All allowed; the assignment form shows workload and same-day conflicts; Overloaded (>100% of 7-day capacity) triggers a **warning with required acknowledgement** by the assigner (not a hard block; Owner/CEO may assign anyway). Sorted by the priority engine. Overdue alone is not labelled "unproductive" — approved blockers/extensions and workload are displayed with it. |
| 5 | **Deadline changed multiple times** | Each change appends history and increments `deadline_version` and `extension_count` (only for later dates). Original untouched. Reminders for the old version can never fire; new version gets a fresh schedule. Dashboards flag tasks with ≥ 3 extensions. Shortening a deadline is allowed, notifies the employee, and requires a reason. If the new deadline is still in the past, task remains overdue. |
| 6 | **Task becomes overdue** | Scanner sets `overdue_since`, `delay_explanation_required=1`, sends overdue notifications (employee, manager, CEO, Owner per rules), employee sees red banner + gate. Status doesn't change. Only for open statuses; Under Review is *not* overdue-by-employee (clock paused at submission, ✱Q: default = overdue stops accruing to the employee while waiting for reviewer, but flag stays visible to management as "waiting on review"). |
| 7 | **Multiple delay explanations** | Allowed and expected (append-only). The latest is shown first, all visible. A new one is required again after a missed *revised* deadline or per Q13. Each can be reviewed separately; earlier decisions never rewritten. |
| 8 | **Employee reports a blocker** | Blocker row + event; if `blocks_work`, task → Blocked and timer auto-paused (`end_reason=blocked`). Managers notified via rules. Overdue clock **keeps running** (the deadline is a commitment) but the delay form pre-links the blocker and reports show "overdue while blocked X h" so it's not read as idleness. Manager may extend the deadline in one step from the blocker screen. On resolve → previous status restored. |
| 9 | **Completed after the deadline** | Allowed. `completed_at > due_at` ⇒ report flag "late completion", lateness duration stored (derivable). If no delay explanation was submitted, completion submit is **blocked until one is** (one-line minimum). Overdue flag cleared; reminders stop. On-time rate counts it as late. |
| 10 | **Manager reverts a completed task** (e.g. QA finds the feature not working; the employee had self-completed) | Revert = Completed → Reopened; needs permission + reason code + note. Status → Reopened, `completed_at` retained in history, new `deadline_version` only if the manager sets a new deadline (else the old, possibly past, deadline applies and the task is overdue immediately → explanation rules apply; UI strongly prompts for a new deadline). Reminders re-armed; stats count reopen events ("rework"). |
| 11 | **Employee forgets to stop timer** | Follow [SRS §6](02-SRS.md): check-ins at 4 h/8 h; hard auto-close at 10 h or 23:59 company time; auto-closed time is *provisional* until the employee confirms (may only shorten, using the last-activity suggestion) or the manager approves/trims; manager alerted after 3 unconfirmed days. Closing the browser alone never stops the timer. |
| 12 | **Internet loss** | Timer state lives on server; the UI shows "offline" but local clock keeps displaying. Actions needing the server (pause/stop) are queued locally *with their client timestamp only as a hint*; on reconnect they are sent and the server records its own time, flagging a `client_offset` if > 2 min so the employee can request a correction. Nothing is silently back-dated. Page refresh re-hydrates from `/time/active`. |
| 13 | **Email delivery fails** | `email_logs.status=failed` after retries 1m/5m/30m/2h/12h; in-app notification still delivered. Permanent failures (invalid address/bounce) mark the user's email as problematic and alert Admin. Mandatory notices (overdue escalations) additionally appear as banners. Admin can retry/resend from UI. Provider outage ⇒ queue grows, outbox never loses events. |
| 14 | **Reminder job runs twice** | `reminder_log` UQ `(task, rule, deadline_version, assignee)` + `INSERT … ON DUPLICATE` semantics ⇒ second run inserts nothing, sends nothing. Notifications have `(user, dedupe_key)` UQ. Beat is single-instance with `GET_LOCK` guard; workers use `SKIP LOCKED`. Verified by a test that executes the scanner twice and in parallel. |
| 15 | **Task is cancelled** | Reason required. Active timer stopped (`end_reason=cancelled`), reminders stop (scanner excludes status), open blockers auto-closed, overdue flag cleared, notifications to assignee + resolved managers. Time logged so far is retained for reporting. Only Owner/CEO can restore. |
| 16 | **Employee assigned by multiple assigners** (there is one Manager, but Owner, CEO, Dept Heads and the Manager can all assign) | Allowed. Each task retains its own `assigned_by`; the employee sees all, ordered by the priority engine. If two managers set conflicting priorities/deadlines on **same-day** work the assignment form warns the second assigner (conflict panel) and both managers get a "workload conflict" notification; resolution is human: the common superior (Dept Head → Manager → CEO) can set `manual_rank` to dictate order. Employee can raise a *question/conflict* comment which notifies all assigners. |

## Additional rules found during analysis
17. **Under Review & overdue**: see #6; reviewers have an SLA (default 2 working days) with its own reminder to the reviewer; escalates to reviewer's manager. ✱
18. **Self-approval**: reviewer ≠ assignee unless Owner.
19. **Assignee on leave**: `on_leave` status warns assigners; reminders are not suppressed automatically (✱ policy), but manager gets "assignee on leave with tasks due" daily digest.
20. **Concurrent edits**: optimistic `version`; the second writer gets 409 and a diff.
21. **Time zones/DST**: instants stored UTC; "end of day" computed in company tz using IANA rules; tests across DST boundaries.
22. **Duplicate submission** (double click): `Idempotency-Key` on creation/transition endpoints; state machine rejects repeated transitions.
23. **Deleting data**: no hard-delete of tasks, history, comments, delay reasons; Owner can only archive/cancel. GDPR-style erasure handled by anonymising the user (name → "Former employee"), keeping task facts.
24. **Role downgrade while holding tasks/reviews**: reviews move to the next eligible reviewer; in-flight sessions unaffected; audited.
25. **Hierarchy cycle or two primary managers**: rejected at DB (unique active key) and service (CTE check).
26. **Estimated hours exhausted** (actual > estimate): informational notification to assignee + assigner at 100% and 150% (configurable) — not an accusation; never auto-stops work.
27. **Bulk operations** (priority change/reassign of 50 tasks): processed per task with per-task authorization & audit, notifications coalesced into one digest per recipient.
28. **Clock skew between servers**: all "now" values from DB `UTC_TIMESTAMP(6)`, not app hosts.
