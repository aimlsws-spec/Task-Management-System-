## Phase 3 — Projects & tasks: done
**Assigning.** Owner/CEO pick a person from the employee list (with each person's current load) and assign directly. The Manager assigns to anyone in their team including department heads, and each head assigns within their department. Rules enforced on the server: nobody assigns upward or outside their scope, nobody assigns to themselves, the Admin never receives tasks, deadline must be in the future, date-only deadline = end of day (18:30 company time).
**Loop and tracking.** The assignee sees the task in *My tasks*; their head, the Manager, the CEO and the Owner see it through their scope; the creator keeps seeing what they assigned. Every action (create, edit, reassign, priority, acknowledge, cancel, attach) is written to the task's activity trail with who/when/before/after, plus status history, assignment history and an initial deadline-history row.
**Workload.** `GET /workload` and the *Team workload* screen show, per person: open tasks, split by priority and status, overdue, due in 7 days, estimated hours vs next-7-working-day capacity (calendar-aware), and a Normal/High/Overloaded level. Owner/CEO see everyone, Manager the team, heads their department. The same numbers appear next to each person in the assign screen.
**Also built:** task list (priority-engine order: overdue → priority → deadline), filters, task detail, edit, reassign, priority change, cancel, acknowledge, projects, categories/types, secure attachments (type allow-list + file-signature check, 25 MB cap, random storage names, authorization re-checked on every download).

## Phase 4 — Employee workflow, completion & time tracking: done
**Timer.** The employee starts, pauses, resumes and stops work on a task. The *server* measures every second; the browser only displays. One running timer per employee: enforced by a row lock *and* a database unique key (proved by a real two-thread race test and a random-sequence property test). Starting a second timer is refused with a clear message and offers "Switch". Refreshing, closing the browser or logging in elsewhere never loses the timer.
**Effort numbers.** Per task: estimated, active (worked), remaining, elapsed since assigned, assigned→started latency, and a session list. Workload now counts what is *left* to do, not the full estimate.
**Forgotten timers (Q9).** Closing the browser does not stop a timer. "Still working?" check-ins after 4 h, 8 h and in the evening (19:00 company time), created once each; hard stop at 10 h of continuous work or 22:00 company time. Auto-stopped time is kept but flagged *provisional*; the employee confirms it or shortens it (never lengthens it), and a running session never counts past its cap even before any job closes it. The same guard runs on any contact and via `POST /admin/jobs/timer-guard`; Phase 6 will schedule it.
**Missing time.** The employee requests it; a manager in scope approves or rejects (nobody approves their own time); overlaps with recorded time are refused. A manager can adjust a closed session; the original values are kept in a correction record.
**Finishing work.** The employee records *progress* (append-only), can put a task *on hold* (stops the clock, needs a reason), and **marks it complete with an assurance** (what was done, tested yes/no + notes, optional evidence link; if no time was tracked they must say why). Review stays optional: tasks of a "review" type, or any task the employee chooses, go through *submit for review → approve / send back*.
**Management side.** *Verify* a completed task (optional) or **Revert** it with a reason code (QA defect, incomplete, requirement changed, other), who found it, and a note: the task returns to the assignee as *Reopened*, the earlier completion stays on record, and the rework is counted. Nobody verifies, reviews or reverts their own work (the Owner excepted).
**Screens.** A timer bar that follows you around the app (with the check-in prompt), the full task page (start/pause/stop, progress, hold, complete dialog, review/verify/revert, time card, completion history), **My Day** dashboard (new tasks to acknowledge, what to do next, deadlines, own workload, auto-stop confirmations; managers also see "needs your attention"), and a **Time** page (own or team sessions, adjustments, missing-time queue).
**Verified:** 631 backend tests on MySQL (incl. permission matrix for every new endpoint); frontend type-check and build clean; the whole flow run live (start → progress → complete → verify → QA revert → employee sees it reopened).

## Phase 5 — Deadlines, overdue & delay accountability: done
**Changing a deadline.** Owner/CEO any task; the Manager within their team; a Department Head within their department. Every change needs a reason (10+ characters) and is stored as history: who, when, from → to, why. The **original deadline can never change**, from any code path (enforced in the data layer, not only in the screens). Later dates count as *extensions* (the task shows "extended ×N"); earlier dates are allowed as *shortened* and do not count. Each change bumps a deadline version, which Phase 6 reminders will key on so an old reminder can never fire after a change.
**Extension requests.** Employees cannot change a deadline; they ask, with a reason. A manager in scope approves (optionally for a different date) or declines with a note; nobody decides their own request, and a request that a manager has already overtaken is refused rather than moving the deadline earlier.
**Mandatory delay explanations.** When a task is past its deadline the assignee sees a red banner and a blocking dialog on the task, and the task is flagged "Explanation needed" in lists and on the dashboard. It cannot be dismissed for good (it returns each time the task is opened) and the task **cannot be completed or submitted** until an explanation exists (a one-line reason while finishing is recorded as a full explanation). The form captures reason, progress, work done, remaining work, blockers and expected completion. Explanations are append-only: no edit, no delete, only newer updates.
**Manager decisions.** Accept, ask for more information, do not accept, approve a revised deadline (which goes through the same history), or escalate. *Accepting never completes the task.* Asking for more or not accepting brings the requirement back until the employee sends a newer explanation. An explanation that is several days old with the task still overdue must be refreshed (3 days, configurable). If a revised deadline is missed too, a fresh explanation is required for the new deadline; earlier ones stay as history. Nobody reviews their own explanation.
**Escalation tiers.** The +1, +3 and +7 **working-day** milestones after a deadline are computed (Sundays, 2nd/4th Saturdays and holidays skipped) and shown as "Escalation 1/2/3". Phase 6 will send the notifications.
**Screens.** Deadline card with original/current/extension count and full history; request-more-time and change-deadline panels; the explanation form and gate; explanation history with decisions; **Delays & Extensions** queue for managers (no explanation yet, awaiting decision, extension requests); dashboard banners and counts; badges in task lists.
**Verified:** 740 backend tests on MySQL (incl. the permission matrix for every new endpoint); frontend type-check and build clean; the whole flow run live on the real clock (deadline passes → gate → explanation → manager accepts, task stays open → revised deadline → history intact).

## Phase 6 — Notifications, reminders & background jobs: built, awaiting your review
**Who is told (and nobody else).** Recipients are described by relationship, never by name: the assignee, who assigned it, the assignee's line manager, the department head, "the Manager above them", everyone with the CEO/Owner role. Owner assigns ABC → ABC, the Developers Head, the Manager and the CEO are told (the Owner, who did it, and unrelated departments are not). One person who qualifies for several reasons gets ONE notification listing all of them; a unique key makes a duplicate physically impossible. Manager-assigned tasks do not involve CEO/Owner unless the Admin switches that rule on. All of this is a table the Admin edits (enable/disable, in-app/email, mandatory, urgent), with the brief's event table seeded as defaults.
**Channels.** In-app notifications (bell with live unread count, a notification centre grouped by day, deep links to the task) and email (HTML + plain text, links back to the task, user text always escaped). People can mute optional notices per channel; **mandatory notices (your task, your deadline, overdue) cannot be muted**.
**Automatic reminders and escalation.** 24 h and 2 h before the deadline; at the deadline (overdue: employee, Head, Manager, CEO and Owner); +1, +3 and +7 **working days** after (employee reminder; then Manager and CEO; then the Owner as well). Each fires exactly once per deadline. Never for tasks on hold, waiting for review, cancelled or finished; never for a deadline that has since changed; a task given only a few hours gets no "24 h before" reminder. A queued reminder (notification or email) is re-checked just before delivery and dropped if it is no longer true. The timings are editable by the Admin.
**Forgotten timers.** The "Still working?" check-ins, automatic stop and the 3-day "unconfirmed time" alert to the manager are now real notifications.
**Email delivery.** Pluggable backend: `log` (default, writes to the server log) or real SMTP (verified end to end against a local SMTP server in the tests). Failures retry with backoff (1 min, 5 min, 30 min, 2 h, 12 h) then show as failed with the reason; a refused recipient fails at once; the in-app notification is never affected; the Admin can retry. Routine email is held for working hours (09:30–18:30 on working days); urgent email goes out immediately.
**Jobs.** A scheduler inside the API process (no Celery/Redis: see [ADR 001](adr/001-background-jobs-without-redis.md)) relays events, scans reminders, runs the timer guard and sends email every few seconds. Only one scheduler runs even with several API processes (a MySQL lock). A failing step is recorded for the Admin and never stops the others.
**Real time.** WebSocket push (single-use tickets, no token in a URL) with automatic reconnect; the bell also polls every 30 s as a fallback. Live check: a page was told in 1.8 s.
**Admin screen.** Notifications & Jobs: scheduler/email health, recent failures, run-a-pass-now; who is notified of what; reminder timing; email log with retry.
**Verified:** 905 backend tests on MySQL (incl. permission matrix for every new endpoint); frontend type-check and build clean; the chain run live on the real clock with the real scheduler (assignment → push → right recipients → deadline passes → scheduler raises the overdue notices → emails sent).

### Email: configured on this machine
Outgoing email uses the company mailbox at `mail.viralkar.in` (SSL, port 465). The server was identified from the domain's own mail records and its TLS certificate before any login. The settings and password live only in the git-ignored `backend/.env`; this file and the docs hold no credentials. A test email to the mailbox itself was accepted by the server (`python -m app.cli send-test-email --to <address>` repeats it).
Safeguards: emails to reserved test addresses (the demo accounts' `@demo.example.com`, `.local`, `.test` ...) are **skipped with a recorded reason** whenever a real mail server is in use, so demo data never bounces. ## Phase 7 — Blockers & communication: built, awaiting your review
**Blockers.** The assignee reports a problem with a type, title, description, impact and what is needed. If it stops work, the task becomes **Blocked**, the timer stops, and waiting time is recorded **apart from working time** (overlapping blockers count once). A manager in scope acknowledges, assigns an owner, replies, escalates or resolves; the raiser confirms (close) or reopens. When the last blocking blocker clears the task returns to its **previous status**. A non-blocking issue changes nothing about the work. Cancelling a task closes its blockers; reassigning keeps it blocked for the new owner. A blocked task cannot be completed. Every step is stored as blocker history.
**Who is told.** The assignee (confirmation), line manager, department head, the Manager and whoever assigned the task hear immediately; the CEO and Owner as well for **critical** tasks; escalation reaches the whole line up to the Owner. Resolution reaches the raiser (mandatory). All rules are Admin-editable.
**Discussion.** Comments, questions, clarifications and threaded replies on each task, with @mentions limited to people involved (assignee, assigner, reporting line, head, CEO/Owner). Questions notify the assigner and manager; replies notify the original author. Authors can correct their own comment for 10 minutes (original kept in the audit trail); nothing is deleted.
**Screens.** Blockers section and "Report a blocker" on the task; Discussion thread with mention picker; **Blockers** queue for managers (open / resolved / closed); dashboard "Open blockers" count; blocked time in the Effort card; new activity labels.
**Verified:** 1047 backend tests on MySQL (30 new for blockers/comments plus 16 permission-matrix rows); frontend type-check and build clean. Live end-to-end check on the running API not yet done.

## Projects, points and the review chain: built (2026-11-17), see [ADR 003](adr/003-projects-points-and-review-chain.md)
**Project.** Name, expected result, optional head, optional team and a list of **points** (work you know about but have not assigned). Points can be added, edited and removed at any time, and each is assigned to an employee when ready (that creates a normal task in the project). With no head, tasks are assigned directly; with a team, only team members can receive tasks. The head is told about every task in the project and can see them all.
**Review chain (project tasks).** Employee marks done -> *Under review*, waiting for the **project head** (if any) -> head approves -> waiting for **CEO or Owner** (either one) -> marks reviewed -> *Completed*. Either reviewer can send work back. Without a head it goes straight to CEO/Owner. Tasks outside projects keep the old flow.
**Project completion.** When every point is assigned and every task is completed or cancelled the project is *ready for review*; Owner and CEO are emailed and either marks it completed. Adding a point later reopens it.
**Where to see it.** *Projects* (everyone sees their own), project page, Dashboard card "Project work waiting for your review", Tasks filter "Waiting for my review".
**Email after deployment.** Links come from `TMS_APP_BASE_URL` (Admin page warns while it is localhost); mail carries Date/Message-ID headers; see SETUP section 7 for SPF/DKIM.
**Verified:** 1,241 backend tests on MySQL (26 new project tests, permission-matrix cells for every new endpoint); frontend type-check and build clean.

## Grace period before "late" (2026-11-17)
A task is **not late until 40 minutes after its deadline** (`TMS_OVERDUE_GRACE_MINUTES`, default 40; set 0 for none). Until then it is not "Overdue", completing it asks for no reason, and no overdue email/escalation is sent. After that the employee must write a reason when finishing (a multi-line box appears; it also appears automatically if the deadline + grace passes while the page is open). The deadline itself is unchanged and is still what is shown and reported. One shared rule (`app/core/grace.py`) is used by task lists, delay gates, reminders, reports and workload so they always agree.
